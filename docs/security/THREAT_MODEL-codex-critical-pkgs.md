# Overview

TAG (Terminal Agent Gateway) is a local-first AI-agent orchestration system delivered in two substantial implementations: the Python package under `src/tag/` and the native Go harness under `tag-go/`. It manages model-backed runs, autonomous loops, cron and queue workers, swarms, CI workflows, memory, evaluations, notifications, profile configuration, credential import, and tool execution. The primary user is a developer or operator who installs TAG on a workstation or automation host and intentionally grants it access to source trees, model credentials, and external services. The repository also contains a thin npm launcher, a web frontend, deployment material, tests, and design documentation; those are secondary to the Python and Go runtime surfaces.

The system's most security-sensitive capability is turning natural-language content and model output into actions. Those actions can read or modify repositories, execute shell commands, start detached workers, call MCP tools, install or enable extensions, send network requests, and invoke remote LLM providers. TAG therefore occupies a privileged position between untrusted task content and valuable local or remote resources. Its important assets are:

- model, cloud, messaging, GitHub, SSH, and other credentials imported into per-profile environments;
- source code, working trees, generated patches, commits, and any other files reachable by a run;
- the integrity of commands, tool calls, queue jobs, scheduled work, issue/PR actions, and outbound notifications;
- persistent prompts, model responses, memories, traces, cost records, webhook payloads, rules, and operational history in the WAL-mode SQLite runtime store;
- model budgets and operator accounts or external services reachable through provider and MCP credentials;
- the integrity of configuration, bundled registries, installed plugins, managed runtimes, and sandbox/permission policy.

The Python controller and command modules (`src/tag/controller.py`, `src/tag/core/run.py`, `src/tag/core/db.py`, and `src/tag/cmd/`) manage profiles, managed runtimes, subprocesses, queues, and many compatibility features. The Go harness (`tag-go/cmd/tag/` and `tag-go/internal/`) supplies a provider-neutral agent loop, built-in tools, MCP client/server integration, HTTP surfaces, permissions, guardrails, and OS or Docker isolation. Security review must cover both implementations rather than assuming one is merely test or migration code; the README documents both as shipped editions with overlapping but non-identical command sets.

# Threat Model, Trust Boundaries, and Assumptions

## Actors and trust boundaries

1. **Operator to privileged local runtime.** CLI arguments, environment variables, profile YAML, permission and guardrail rules, configured work directories, provider base URLs, webhook secrets, and extension choices are operator-controlled. The runtime may execute with all permissions of the invoking OS user. The local operator is trusted to choose intended capabilities, but parsing, path resolution, and default behavior must not silently grant more authority than requested.

2. **Task content and model output to tools.** User prompts may incorporate repository files, issue or webhook text, retrieved web content, memories, tool output, and third-party messages. Any of those can contain prompt injection. Model-generated tool names and arguments are attacker-influenceable even when the model provider itself is honest. Permission checks in `tag-go/internal/permission/`, optional content screening in `tag-go/internal/guardrail/`, and confinement in `tag-go/internal/sandbox/` form distinct controls: permission answers whether a requested tool is allowed, guardrails inspect content, and the sandbox limits what an allowed command can reach. No one layer should be treated as a substitute for another.

3. **Agent process to host filesystem and process environment.** Shell, file, Git, and subprocess features cross from synthesized instructions into host effects. Workspace paths, symlinks, inherited environment variables, child processes, cancellation, and cleanup are security-sensitive. `tag-go/internal/tool/tools.go` includes shell-backed execution, while the Python controller and worker paths launch external programs and managed Hermes processes. The default local OS account is not a security boundary; a successful escape from intended workspace or sandbox scope reaches that account's accessible resources.

4. **Sandboxed workload to host or container infrastructure.** `tag-go/internal/sandbox/` supports OS-specific restricted execution and Docker. The protected boundary includes credential paths, paths outside the selected run directory, host processes, and network destinations. Docker images and code run inside a sandbox are untrusted. Access to the Docker daemon is itself highly privileged. The implementation explicitly distinguishes requested isolation from isolation actually achieved and refuses destination-granular firewall policies on backends that cannot enforce them; review should preserve that fail-honest property.

5. **Local and remote HTTP clients to runtime state or actions.** Python and Go dashboard/dev UI servers expose run, queue, trace, memory, alert, and cost data; most are intended for loopback and deliberately omit wildcard CORS (`src/tag/api.py`, `src/tag/devui.py`, `tag-go/internal/server/`). Python accepts configurable bind hosts, so an operator can intentionally widen this boundary. Webhook receivers (`src/tag/webhook_server.py` and `tag-go/internal/webhook/`) accept Internet-originated payloads that can become queued agent tasks. Gateway or other action-capable HTTP endpoints are more sensitive than read-only dashboards. Loopback is a deployment assumption, not authentication, and malicious local processes, browser-based localhost attacks, reverse proxies, containers, or a non-loopback bind can invalidate it.

6. **External providers, endpoints, and MCP servers to TAG.** Prompts and potentially repository content leave the host for Anthropic, OpenAI, OpenAI-compatible endpoints, embedding services, web services, and configured gateways (`tag-go/internal/llm/`, `tag-go/internal/memory/embed.go`, and Python provider paths). Their responses and streaming frames are untrusted structured input. MCP servers and tools may be local subprocesses or access remote resources; tool responses are untrusted, while MCP actions can carry the authority of configured credentials. A custom `TAG_LOCAL_BASE_URL` or analogous provider URL is operator-controlled, but redirect, proxy, TLS, timeout, and secret-forwarding behavior must still avoid credential disclosure or SSRF surprises.

7. **Registries, marketplaces, plugins, packages, and managed runtimes to executable code.** Profile marketplace URLs, MCP registries, plugin metadata, npm/Python packages, downloaded archives, Git repositories, and container images are supply-chain inputs. Installation or enablement can create executable configuration and later run code with the user's authority. URL validation, private-address/redirect checks, archive traversal defenses, validated profile names, exact dependency pins, and explicit enablement materially reduce risk, but authenticity and provenance remain important. Relevant surfaces include `tag-go/internal/marketplace/`, `tag-go/internal/cli/plugin.go`, `tag-go/internal/cli/mcp_registry.go`, `src/tag/cmd/marketplace.py`, and setup/install paths in `src/tag/controller.py`.

8. **Concurrent processes to persistent state.** Foreground commands, detached queue workers, cron, loops, webhook handlers, and dashboards share SQLite and configuration. Database transactions, parameterized queries, WAL mode, idempotency, atomic file replacement, advisory locks, job state transitions, and migration integrity protect against corruption, duplicate execution, or authorization decisions based on stale state. `src/tag/core/config.py` and `tag-go/internal/config/config.go` use atomic persistence and locks for configuration updates; the runtime database remains a high-value local asset.

## Input ownership

- **Attacker-controlled or attacker-influenceable:** cloned repository contents and filenames; issue, PR, chat, notification, webhook, and retrieved web text; model and MCP responses; tool output; crafted HTTP requests and headers; marketplace/plugin documents and remote archives; remote API error and streaming bodies; malicious symlinks and files within an untrusted workspace; and any prompt-derived shell, file, SQL-filter, URL, or tool argument.
- **Operator-controlled:** CLI flags; profiles and runtime configuration; secrets and environment; selected providers and endpoints; sandbox backend, working directory, images, and egress policy; approval mode; enabled tools, MCP servers, plugins, and webhook rules; bind addresses; and explicit opt-ins such as accepting unsigned webhooks.
- **Developer-controlled:** bundled defaults and registries; schema migrations; dependency and release metadata; embedded web assets; permission defaults; built-in detectors; packaging/launcher behavior; and repository-provided deployment templates.

Content does not become trusted merely because it is stored in SQLite, returned by a known model, signed by a webhook provider, or emitted by an enabled MCP server. A valid webhook signature authenticates the sender, not the safety of issue text. Likewise, operator selection of a repository or plugin does not make every file inside it benign.

## Security invariants and assumptions

- Every action-capable remote or cross-origin request must be authenticated or be gated by an explicit, accurately described operator opt-in. Webhook text must not enqueue work before signature policy is enforced.
- Model output and prompt-derived data must not bypass the same permission, approval, content-screening, workspace, and sandbox checks applied to direct tool requests. In non-interactive operation, an `ask` decision must resolve to deny unless an explicit out-of-process approval mechanism is active.
- File operations must remain within their documented roots after canonicalization and symlink handling. Restricted runs must not expose credential stores or unrelated host paths. Security status output must describe effective rather than merely requested isolation.
- Secrets must not be sent to an unintended provider or host, written into broadly readable files, surfaced in logs/UI/errors, embedded in prompts without need, or stored in unredacted audit records. Provider credentials must not follow redirects or custom endpoints contrary to the selected trust boundary.
- Untrusted strings must remain data across shells, SQL, YAML/JSON, HTML, terminal output, HTTP headers, archive extraction, and Git/process invocation. Structured argument APIs and parameterized queries are preferred; any intentional shell evaluation is an explicit high-risk sink.
- Queue, cron, loop, swarm, webhook, and CI paths must preserve job identity, budget, cancellation, timeout, and approval semantics across restarts and concurrency. A failure to launch or persist must not be reported as completed, and replay must not duplicate privileged work.
- HTTP request bodies, SSE/streaming responses, model output, subprocess output, database queries, and worker populations need bounds. An untrusted request or routine provider failure must not cause unbounded memory, threads, disk, processes, retries, or spend.
- Installed or enabled extensions must not escape intended destination paths during download/extraction, reach prohibited network locations through URL tricks or redirects, or become active under a misleading provenance claim.

The baseline deployment assumption is a single trusted local OS user, with dashboard-style servers bound to loopback and profile/config/database files protected by normal per-user filesystem permissions. An attacker who already controls that same account can generally edit configuration, replace binaries, read the database, and steal keys; defending against that fully is out of scope. However, untrusted repositories, model content, webhooks, remote services, and plugins are in scope precisely because they are processed within that account. Features intentionally exposed to a LAN/Internet or run in shared CI require explicit authentication and network-layer protection beyond loopback defaults.

# Attack Surface, Mitigations, and Attacker Stories

## Agent execution, tools, and prompt injection

The central attacker story is a malicious repository file, issue body, webhook, webpage, memory, or tool result instructing the model to read credentials, alter unrelated files, execute a destructive command, or invoke a privileged MCP action. A robust flow keeps generated calls behind `tag-go/internal/permission/`, whose built-in defaults protect credential paths and treat unknown/MCP/plugin tools as approval-requiring, and then behind the sandbox where applicable. Headless `ask` behavior is documented to deny. `tag-go/internal/guardrail/` can screen tool inputs, tool outputs, model output, and user input and fails closed for configured rules it cannot evaluate, but no-rules mode is intentionally inert. Bugs that skip registration/gating on one execution path, confuse tool identity, incorrectly cache approval, or allow prompt text to become a shell command without intended approval are important repository-wide risks.

Budget enforcement, iteration caps, cancellation, tool limits, and provider timeouts are also security controls. An attacker may try to create recursive jobs, huge prompts, costly fallback chains, retry storms, or many detached workers. These can deny service, consume paid tokens, fill SQLite or logs, and obscure malicious actions even without code execution.

## Filesystem, subprocess, Git, and isolation

Shell commands are intentionally supported. The critical distinction is whether a command was explicitly authorized and what it can reach. Command strings, working directories, environment, interpreter selection, file arguments, and Git refs may originate in untrusted content. Path-prefix checks without canonicalization, unsafe symlink following, argument-to-shell interpolation, writable wrapper/config injection, or inherited secrets can turn a bounded action into arbitrary host access.

The Go sandbox contains several material mitigations: explicit run-directory validation; OS-specific restricted backends; Docker resource/network options; protected credential paths; timeouts and cleanup; firewall policy validation; and result text intended to state actual confinement. The firewall design in `tag-go/internal/sandbox/firewall.go` refuses per-destination policy on restricted backends that cannot enforce it and pins resolved hosts for Docker. Relevant attack stories include sandbox profile injection, symlink or mount escape, unsafe Docker flags or image entrypoints, incomplete process-group termination, DNS/redirect bypass of egress rules, reachability of host or cloud-metadata addresses, and an isolation fallback that silently runs without promised controls.

## HTTP dashboards, gateway, webhooks, and LSP

The Go dashboard servers bind to `127.0.0.1` and avoid wildcard CORS; Python dashboard/dev UI defaults do likewise. These controls reduce casual network disclosure but do not replace authorization when users can choose `0.0.0.0`, place the service behind a proxy, or browse attacker-controlled pages. Sensitive fields inserted into embedded HTML/JavaScript or rendered dynamically must be encoded for the correct context. Request paths and query values must not become unsafe SQL, file paths, or templates. Slow clients and long-lived SSE connections require concurrency and timeout limits.

Webhook ingestion is action-capable. `src/tag/webhook_server.py` demonstrates expected defenses: HMAC comparison over raw bodies, Slack timestamp freshness, refusal of unsigned events unless explicitly enabled, replay tracking, a 10 MiB body cap, socket timeouts, bounded introspection access, and job-state updates that do not report success before enqueue. The Go counterpart should uphold equivalent properties. Realistic attacks include forged or replayed deliveries, ambiguous signature/header parsing, unsigned-default regressions, trigger-rule filter bypass, crafted event text becoming an agent prompt, request floods exhausting threads/storage, and introspection endpoints leaking event metadata or automation rules.

The LSP TCP mode and model-compatible gateway are additional local protocol boundaries. If bound beyond loopback or launched in shared environments, unauthenticated requests may expose workspace data or invoke model/tool capabilities. Protocol parsers must bound message sizes and recover from malformed peers.

## Providers, credentials, and outbound network

Credential importers read other tools' local stores and write profile environments. The protection objective is least dissemination: import only the requested value, set restrictive permissions, avoid command-line or log exposure, and associate it with the intended provider. Custom endpoints, proxies, fallback chains, redirects, and MCP configuration complicate that association. A malicious endpoint may return malformed SSE/JSON, oversized data, tool-call injection, deceptive error messages, or redirects designed to receive an Authorization header. Provider response parsing in `tag-go/internal/llm/` and equivalent Python paths must enforce timeouts, size/stream integrity, correct TLS defaults, and separation of credentials between fallback providers.

Traces, memories, prompts, webhook payloads, and SQLite history can contain secrets or personal/source data. Dashboards, exports, notifications, and error messages create secondary disclosure channels. The secret scanner and content guardrails are useful mitigations but pattern matching is not a guarantee; data minimization and contextual redaction remain necessary.

## Extensions, marketplace, MCP, and supply chain

Remote marketplace and plugin inputs may control names, URLs, metadata, configuration fragments, archive members, executable commands, or package coordinates. Realistic attacks are SSRF into loopback/private/cloud-metadata services, redirect-based allowlist bypass, archive traversal or symlink extraction, profile-name path traversal, dependency confusion, malicious lifecycle hooks, and enabling a high-authority MCP server under misleading metadata. Existing tests and code indicate private-address URL guards and traversal validation, while exact Python dependency pins reduce opportunistic package drift. Those are meaningful mitigations, not proof of authenticity. Installed code and remote container images remain trusted only to the degree explicitly accepted by the operator and confined at runtime.

MCP is a two-way boundary: TAG can connect to external servers, and `tag mcp-serve` exposes built-in tools over stdio. Tool schemas, notifications, IDs, response bodies, subprocess lifetime, and server command configuration are untrusted. Unknown MCP actions should retain permission defaults and cannot inherit blanket approval merely because the server itself was enabled.

## Persistence, concurrency, and rendering

SQLite contains operational state that affects future privileged work. Parameterized SQL, WAL mode, schema initialization, atomic state transitions, locks, and idempotency reduce injection and race risks. Attack stories include query construction from filters, malicious JSON/YAML types, lost-update races in config, duplicate queue claiming, inconsistent webhook/job status, stale PID reuse, unsafe migrations, and stored active content later rendered in dashboards or terminals. Terminal escape sequences and HTML/JavaScript context injection matter because model/tool output is attacker-controlled even on a local UI.

## Lower-priority or out-of-scope stories

- Direct modification by the already-compromised local user of their own TAG database, configuration, runtime, executable, or credential files is not a meaningful privilege escalation, though safe failure and corruption resistance still matter.
- Read-only localhost metadata exposure is normally less severe than remote command execution, but becomes more important if browser cross-origin protections, host checks, proxying, or bind defaults fail.
- A provider merely seeing content the operator knowingly configured it to process is expected behavior. Sending unrelated secrets, crossing provider/profile boundaries, or sending content to an endpoint different from the one shown is in scope.
- Developer-only test fixtures and documentation are not production attack surfaces unless packaging, setup, CI, or runtime code consumes them. Conversely, cron, queue, webhook, plugin, MCP, and sandbox paths remain production surfaces even when optional because the repository advertises and ships them.

# Severity Calibration (Critical, High, Medium, Low)

## Critical

Use critical for a broadly reachable failure that crosses the central automation boundary and yields arbitrary code execution or comparable compromise with little/no trusted-user interaction, especially when network-exposed or affecting the extension supply chain. Examples include an unauthenticated webhook/gateway request that reliably executes arbitrary host commands with imported credentials; a default sandbox escape reachable through ordinary hostile repository content that compromises the host; or a marketplace/install traversal that causes automatically activated code execution across typical installations. Critical also fits compromise of signing/update infrastructure that turns an ordinary trusted installation into code execution for many users.

## High

Use high for substantial compromise of a user's workspace, credentials, external accounts, or automation where exploitation requires a plausible feature choice or attacker-controlled task input. Examples include bypassing permission/sandbox checks so a malicious repository or signed issue text reads SSH/cloud keys or writes outside the workspace; webhook authentication or replay failure that lets an attacker enqueue arbitrary privileged agent work on an exposed receiver; SSRF with useful access to cloud metadata or local administrative services; arbitrary file write through plugin/archive/profile handling; or cross-provider credential leakage through redirects or endpoint confusion. A reliable denial of all agent service or uncontrolled paid-model spend may also be high when remotely triggerable and unbounded.

## Medium

Use medium for meaningful but contained confidentiality, integrity, or availability impact with stronger prerequisites, reduced authority, or recoverable scope. Examples include cross-origin access to sensitive local run/prompt/cost history; stored dashboard or terminal injection requiring the operator to view a malicious run; a bounded request/stream causing worker or server exhaustion; a race that duplicates a limited job or corrupts recoverable queue/config state; prompt/tool data leaking to the correct provider but outside the intended profile; or sandbox policy inconsistency that expands access only within a low-value disposable workspace. A finding that needs an explicit unsafe opt-in, such as unsigned webhooks or a non-loopback bind, is generally reduced unless the code misrepresents that risk.

## Low

Use low for limited local-only impact, minor information disclosure, or robustness failures that do not cross a meaningful privilege boundary. Examples include exposing non-sensitive health/version metadata on loopback; crashing one interactive invocation on malformed local input without persistent corruption; incomplete redaction of low-sensitivity operational metadata; or a misleading but non-security-relevant status field when enforcement remains correct. Pure best-practice gaps, hypothetical issues with no attacker-controlled path, and attacks requiring control of the same OS account with no additional authority should normally be informational or not reportable rather than inflated to low.
